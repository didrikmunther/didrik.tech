CalliQ listens to phone calls in real time.
When a caller seems to be attempting a scam, CalliQ warns the person receiving the call while they're still on the line.
We built three views: the caller in a browser, the receiver on a phone, and a dashboard that shows the transcript as it comes in.
On stage at Microsoft in Stockholm, we demoed it with a live call between two devices.
The caller's browser records the microphone, downsamples the audio to 16 kHz, and streams it over a WebSocket to our Python backend.
The backend connects the caller to an available receiver and transcribes the audio with Azure AI Speech, building up a transcript as the conversation goes on.
After each new sentence, an agent built with LangGraph and GPT-4o mini reads the conversation so far and decides whether the receiver is about to be scammed.
If so, the agent calls a warning tool with a short explanation, and the backend sends that warning straight to the receiver's phone.
We asked the model to keep its warnings friendly and easy to understand.
Instead of a generic alarm, the warning explains what looks risky:
It's not safe to share your bank account details with anyone over the phone, especially if they are asking for it unexpectedly.

In February, I took part in HackEurope, where we built Optimera: a prototype that uses application traces to find slow database calls and asks a coding agent to propose a fix.
The idea came from a familiar problem.
You know an application is slow, but finding the query responsible still means moving between telemetry, logs, and source code.
We wanted to connect those steps so that a performance problem could arrive with a proposed code change to review.
The summary chart and improvement percentage are demo data, not measured performance results.
Screenshots from Axel Dovskog's project page.
From a trace to a proposed fix
Our demo application used Express, Prisma, and PostgreSQL.
OpenTelemetry recorded its execution, and Jaeger collected the traces.
A Django backend scanned them for slow operations, while a React dashboard showed the incidents and suggested changes.
Find a slow trace and identify the slowest instrumented Prisma call within it.
Read the source location attached to that call.
Give Claude Code the repository and a focused task: improve performance around that location while preserving the output.
Commit the proposed change on a separate branch and open a pull request for review.
The dashboard let us inspect the proposal and choose whether to merge or reject it.
The agent's output was a candidate fix that still needed review.
Keeping the source location through async calls
I worked on the tracing and instrumentation that connected database operations back to the application code.
A duration tells you where time went, but the agent also needs to know where to start editing.
One awkward detail was Prisma's lazy execution.
Calling a Prisma method creates a promise-like object; the query starts when that object is awaited.
Capturing context around the initial method call wasn't enough, because that context could be gone by the time the query actually ran.
The prototype wrapped Prisma calls to capture the application stack and the active OpenTelemetry context.
It then restored that context when Prisma's promise executed.
This let us attach the originating source frame to the query's span, alongside the model, operation, and arguments.
That connection was the useful part: a slow operation could point to a specific place in the repository, instead of leaving the coding agent to search the entire application.
A concrete example: the leaderboard
The demo included a leaderboard endpoint that first loaded all models, then fetched matches separately for each model.
That's an N+1-query pattern: one initial query followed by another for every item.
The generated change below fetched the relevant match fields once and calculated each model's wins and totals in memory.
It removed the repeated per-model queries.
Loading those matches into memory has its own scaling limit, so this was a concrete optimization to inspect and benchmark, rather than a universal solution.
The proposed leaderboard change: fewer database round trips, with the implementation available for review.
Giving the agent a useful starting point
Optimera brought together two pieces: telemetry showing where an application spent time, and a coding agent that could act on that evidence.
Getting useful source locations through the instrumentation was what connected them.
For this prototype, we focused on Prisma queries and N+1 patterns.
Extending it would mean supporting more libraries and checking proposed changes against both expected behaviour and representative workloads.
A pull request makes the suggestion inspectable; tests and measurements are what would give us confidence to ship it.
The source code is on GitHub, and our original hackathon submission includes the demo.
Rost is a statically typed programming language I've built in Rust.
It has generics, type checking, error messages that point to the exact code, and a language server for VS Code.
The compiler outputs Python or WebAssembly, and you can try it in your browser.
The name is Swedish for rust.
I've made a lot of programming languages from scratch, and Rost is the latest one.

From Rost to my master's thesis
Making my own languages is what led me to my master's thesis at KTH.
Editor support like this makes a language much easier to use, but it takes a lot of work to build.
With tools like Langium or Xtext, a language that already has a compiler typically has to implement its semantics a second time to get it.
In Semi-Automatic LSP Server Generation for Domain-Specific Languages, I proposed reusing what the compiler already knows instead: metadata attached during compilation provides language server features such as go-to definition and hover information.
I demonstrated the approach in the Miking language workbench and evaluated it on two domain-specific languages, MLang and ProbTime.
The results show that language support can be derived semi-automatically with minimal manual work.

At Strawberry, we're building AI companions that are delightful and easy to use for non-technical people.
I work on agent behaviour, particularly the memory system and the evaluations we use to test browser use and agent behaviour.
Open the image for a closer look.
Memory is a big part of making a companion feel easy to work with.
Our companions remember your preferences, your workflows, people you work with, and things you do.
This lets you be a little more vague when asking for something, without having to explain your entire workflow again.
How a companion remembers The cover provides context at the start of a conversation; recall brings back details when needed.
Forgotten observations are marked, and that state carries into dreaming.
Our memory system starts with a database of observations.
We create these by forking the user's chat before its cache goes stale or the conversation needs to be compacted.
This gives us a separate continuation of the conversation in which to capture observations.
At night, an agent "dreams" over the day's chats and observations, producing a summary we call a cover.
We inject this into the system prompt, giving the companion background knowledge it brings into new conversations.
This is part of what gives a companion its continuity and "soul."
The observations and original chat transcripts also remain searchable, both by wording and by meaning.
The companion can recall details beyond what's included in its cover.
Research on LongMemEval found that compressing conversations into individual facts hurt overall performance through information loss, although it helped multi-session reasoning.
One thing we learned is that giving an agent freedom to organize its own memory files can backfire.
In our experiments, the files and memories became bloated, and performance degraded.
The models tended to add more text rather than remove it, which made forgetting an essential part of the design.
In our system, forgetting means marking an observation as forgotten.
That state also carries through into subsequent dreams.
It's tempting to let agents manage all of this themselves.
Perhaps they'll become better at it, but today we've found that they need more guidance and constraints to keep their memories useful.
Another interesting challenge is capability awareness: the agent needs to know about its own settings and features, including how they work together.
As we build more functionality, that prompting can become stale or get lost among other instructions.
This is where evaluations, or evals, come in.
We build tests around features and combinations of features to check that the agent understands and uses them correctly.
That includes everything from spreadsheet tasks and navigating broken websites to using memory across multiple webpages.
The evals have also become useful beyond the agent team.
Our go-to-market team builds custom companions for different use cases.
Previously, they would build a companion and manually test it, which takes a lot of time.
Now they can build several in parallel and benchmark them against expected outcomes using deterministic test data.
